# Threat model

AgentRadius is a security tool, so it is itself a target. It aggregates a map of what can reach what, which is valuable to an attacker. This document covers the current MVP and the planned discovery and enforcement phases.

## Assets

| Asset                                      | Why it matters                                                                |
| ------------------------------------------ | ----------------------------------------------------------------------------- |
| The permission graph and findings          | A ready-made attack map: which agent, credential, and role reaches production |
| Credential references                      | They reveal where secrets live, even without the values                       |
| Client configurations (future enforcement) | Rewriting them changes what agents can do                                     |
| Audit log (future)                         | Evidence of what was allowed or denied                                        |
| The user's trust in the labels             | A false "enforced" or "blocked" label is itself a vulnerability               |

## Trust boundaries

1. **Browser ↔ loopback API.** Any website the user visits can send requests to `127.0.0.1`.
2. **Other local processes ↔ loopback API.** Same user, same machine.
3. **Input data ↔ AgentRadius.** Snapshots and, later, config files and connector output are untrusted input.
4. **AgentRadius ↔ the OS.** TCC, SIP, sandboxing, and Keychain protections.
5. **(Future) Agent client ↔ wrapper proxy ↔ MCP server.**

## Out of scope

AgentRadius cannot defend against these, and says so:

- Malware already running as the user. It can read anything the user can, including AgentRadius's memory.
- A compromised OS or root user.
- Exploitability. Reachability results are not proof that an attack works.

## Cryptography

The MVP performs no encryption and stores no secrets. Optional Google sign-in uses SHA-256 for the PKCE challenge and `crypto.randomBytes` for state and session IDs; the client secret is read from the environment and never stored. Planned uses must follow the workspace crypto rule:

- SHA-256 for audit chaining and approval binding.
- Ed25519 for optional audit signing, with the key in the login Keychain.
- AES-256-GCM for any future at-rest encryption.
- Never MD5, SHA-1, DES/3DES, RC4, or AES-CBC/ECB.

The research flagged AGT's Fernet vault (AES-128-CBC with HMAC) as a pattern not to adopt.
